# Задача 1. Создание временной брони

## Цель

Реализовать первый законченный сценарий системы: пользователь отправляет запрос на бронирование комнаты, а сервис создаёт временную бронь со статусом `PENDING`, если комната доступна.

В рамках этой задачи реализуются:

- `BookingService.createPendingBooking(...)`;
- `POST /api/v1/bookings`;
- проверка комнаты и входных данных;
- защита от пересекающихся бронирований;
- Redis-блокировка для конкурентных запросов;
- сохранение брони в одной транзакции.

Подтверждение, отмена и фоновое истечение брони выполняются в следующих задачах.

## Endpoint

`POST /api/v1/bookings`

### Request

```json
{
  "roomId": 1,
  "userId": 42,
  "title": "Архитектурный комитет",
  "startTime": "2026-11-01T14:00:00Z",
  "endTime": "2026-11-01T15:00:00Z"
}
```

### Успешный ответ

HTTP `201 Created`

```json
{
  "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
  "roomId": 1,
  "userId": 42,
  "title": "Архитектурный комитет",
  "startTime": "2026-11-01T14:00:00Z",
  "endTime": "2026-11-01T15:00:00Z",
  "status": "PENDING",
  "expiresAt": "2026-11-01T13:10:00Z",
  "createdAt": "2026-11-01T13:00:00Z"
}
```

`expiresAt` рассчитывается от фактического времени создания: `createdAt + 10 минут`.

## Валидация запроса

До обращения к базе данных проверяются следующие правила:

- `roomId` обязателен и больше нуля;
- `userId` обязателен и больше нуля;
- `title` обязателен, не пустой и не длиннее 255 символов;
- `startTime` и `endTime` обязательны;
- `endTime` строго позже `startTime`;
- длительность брони от 15 минут до 4 часов;
- `startTime` не может быть в прошлом.

При нарушении правил endpoint возвращает HTTP `400 Bad Request` с кодом `VALIDATION_ERROR`.

## Алгоритм сервиса

Метод `createPendingBooking(CreateBookingRequest request)` выполняется следующим образом:

1. Сервис повторно проверяет бизнес-валидацию входных данных.
2. Через `RoomRepository` получает комнату по `roomId`.
3. Если комната не найдена, возвращает `404 ROOM_NOT_FOUND`.
4. Если `room.active == false`, возвращает `409 ROOM_INACTIVE`.
5. Получает распределённую блокировку Redis с ключом `booking:room:{roomId}`.
6. Если блокировку нельзя получить за заданное время, возвращает `409 SLOT_ALREADY_BOOKED`.
7. Внутри `@Transactional` повторно читает брони комнаты со статусами `PENDING` и `CONFIRMED`.
8. Для каждой существующей брони проверяет пересечение интервалов:

   ```text
   request.startTime < existing.endTime
   AND request.endTime > existing.startTime
   ```

9. Если пересечение найдено, выбрасывает `RoomAlreadyBookedException`.
10. Если пересечений нет, создаёт `Booking` со значениями:

    - `room` — найденная комната;
    - `userId`, `title`, `startTime`, `endTime` — из запроса;
    - `status = PENDING`;
    - `expiresAt = now + 10 минут`;
    - `createdAt` заполняется Hibernate.

11. Сохраняет сущность через `BookingRepository`.
12. Преобразует сущность в `BookingResponse`.
13. В блоке `finally` освобождает Redis-блокировку.

Блокировка должна освобождаться независимо от результата операции. Нельзя освобождать её до завершения транзакции.

## Репозиторий

`BookingRepository` должен предоставлять запрос поиска пересечений:

```java
List<Booking> findByRoomIdAndStatusInAndStartTimeLessThanAndEndTimeGreaterThan(
        Long roomId,
        Collection<BookingStatus> statuses,
        LocalDateTime endTime,
        LocalDateTime startTime
);
```

Допускается заменить derived query на `@Query`, если это делает условие пересечения понятнее.

## Обработка ошибок

| Ситуация | HTTP | Код |
|---|---:|---|
| Некорректный запрос | 400 | `VALIDATION_ERROR` |
| Комната не найдена | 404 | `ROOM_NOT_FOUND` |
| Комната неактивна | 409 | `ROOM_INACTIVE` |
| Интервал уже занят | 409 | `SLOT_ALREADY_BOOKED` |
| Ошибка блокировки | 409 | `SLOT_ALREADY_BOOKED` |

## Критерии готовности

- endpoint принимает валидный JSON и возвращает `201`;
- новая бронь сохраняется со статусом `PENDING`;
- `expiresAt` равен времени создания плюс 10 минут;
- неактивная или отсутствующая комната не бронируется;
- пересекающийся интервал отклоняется;
- соприкасающиеся интервалы разрешены: `10:00–11:00` и `11:00–12:00`;
- при 20 одновременных запросах на один слот создаётся ровно одна бронь;
- Redis-блокировка освобождается после успеха и после исключения;
- ошибки возвращаются в едином формате API.

## Минимальный набор тестов

1. Создание брони для активной комнаты.
2. Ошибка при отсутствии комнаты.
3. Ошибка для неактивной комнаты.
4. Ошибка при пересечении с `PENDING` бронью.
5. Ошибка при пересечении с `CONFIRMED` бронью.
6. Успешное бронирование соседнего интервала.
7. Ошибка валидации времени.
8. Конкурентное создание 20 одинаковых броней: одна успешная, 19 конфликтов.
